## Card 1 — Scouting reports (manifest order #1)

- **O3 switch:** `legs_hypothesis = scouting_reports` (default off; default arm runs manifest order R26).
- **Behavior changed:** return to study and plan — the player comes back *between* brackets to read opponents, then enters (R46 return; R51's 2-brackets-in-48h signal).
- **Why it could:** this audience builds parlays from information — 85% of online bettors say researching statistics to bet better is part of the enjoyment (dossier A-3, Siena/SRI 2026); the tendency card (R81) is already the product's tale-of-the-tape, so deepening it extends a validated code (dossier §3.2) rather than adding a foreign one.
- **Minimum fair-test implementation (as built, f7 — now satisfies the card as written, with a legacy-event caveat):** an opponent panel on the **pre-match commit screen** (`app/ui/screens/duel.js`, rendered only when `scouting_reports` is active): the opponent's duel history from the shared ledger, capped at a **last-10** window (`app/engine/hypotheses.js:opponentDuelHistory`, real `DUEL_RESOLVED` events keyed by `characterId`), now including **elements played by round, per past duel** (`playedByRound`/`facedByRound`, oriented via `combatants`) exactly as this card and R26(1) ask for. **Measured depth on this single-device build:** NPC `characterId`s are minted fresh per bracket (`npc-${bracketId}-${i}`, `game.js`) and carry no "same opponent" identity across brackets, so the reachable depth is bounded by the opponent's own prior matches *within the current bracket* — **0 rows at the quarterfinal (no opponent has played yet), 1 at the semifinal, 2 at the final**; per-round scouting is reachable from the semifinal on, never at the quarterfinal. **History of the deviation, resolved at f7:** f1's original A6 ledger slimming dropped the per-round `rounds` array outright, making a per-round move sequence genuinely not reconstructable — recorded as decision-graph node `D-LEDGER-SLIM-VS-SCOUTING`. f6 already changed that premise (a SLIM per-round record is persisted on every `DUEL_RESOLVED` event since f6, for an unrelated fix — the cross-instance reveal-replay crash), but the scouting panel and this document were not updated to use it until now (the stale claim f7 corrects). **Legacy-event caveat:** a `DUEL_RESOLVED` event written before f6 (no migration) carries no per-round record at all; those duels fall back to the ORIGINAL summary fields (**W/L, round score for/against, draws, an affinity-play-rate proxy, transfer, floor-drain/tie flags**), honestly marked (`roundsAvailable: false`) rather than a fabricated per-round guess — read-only, one screen, no push messaging either way.
- **What failure teaches:** information depth is a secondary hook — the audience's research pleasure doesn't transfer to this game's decision, and later envelopes should hunt attachment elsewhere (characters, appointments) rather than deeper data.
- **§13 metrics it reads:** primary — brackets entered/completed per week and the R51 2-brackets-in-48h rate; secondary — D1 return (R46), session pre-match dwell (event-timestamped screen events), replay-after-loss (R49); diagnostic — hesitate rate (a study surface must not push commits past the O5 window; pacing is wrong above 10%).

## Card 2 — Pre-match Narrator brief (manifest order #2)

- **O3 switch:** `legs_hypothesis = prematch_brief`.
- **Behavior changed:** anticipation before commitment — the player treats the next duel as an event worth returning for, raising replay-after-loss (R49) and next-day return.
- **Why it could:** character attachment is the measured differentiator (R30: the character layer carries; R22 measures character recall); the Narrator is the register players praised [TESTED, R71] but today it is a post-duel artifact only — moving its voice *ahead* of commitment converts record-keeping into stakes-setting, the tale-of-the-tape beat every fight broadcast runs (dossier §3.2).
- **Minimum fair-test implementation (as built, f2):** a **two-sentence brief per opponent from the ledger** (`app/engine/narrator.js:generatePreMatchBrief`, rendered on the pre-match commit screen by `duel.js` only when `prematch_brief` is active): register-aware (per-treatment register sets, C5), fed by the same slimmed-ledger opponent summary as card 1 (`summarizeOpponentHistory` — record, W/L, affinity-play-rate proxy), passed through the R73 discipline scanner with a static fallback on any violation. Deterministic template render, not a live model call (consistent with this artifact's simulated-Narrator substitution point); no new art, no sound, no extra screen — the brief renders in the Narrator accent color (R79).
- **What failure teaches:** the Narrator is a post-duel artifact only — its value is closure, not anticipation; anticipation must come from stakes and schedule (cards 4/5), and Narrator spend stays at one call per duel (R72).
- **§13 metrics it reads:** primary — replay-after-loss (R49) and reservation presses (R49a) per R51; secondary — S5 duel abandonment (O9 metric), commit-window hesitate rate (O5, ≤10%), character recall in the cohort open response (R22); guard — Narrator specificity-check pass rate (O10) on the new call site.

## Card 3 — Spectate after elimination (manifest order #3)

- **O3 switch:** `legs_hypothesis = spectate`.
- **Behavior changed:** staying and re-entering — the eliminated player remains in the room, watches the bracket resolve, and re-enters sooner (elimination-to-re-entry time, spectate rate).
- **Why it could:** sync rooms have social pull (R26), and *sweat as content* is a documented behavior of this audience — watching someone else's stake at risk is the whole betting-streamer economy (dossier §3.5: Stake/Kick/Barstool); elimination is currently the product's coldest exit and the bracket it interrupts is already live (R81 board exists).
- **Minimum fair-test implementation (as built, f2):** the **live bracket board stays open to the eliminated player** — the board itself (R81) shipped in t3 and was already reachable; what f2 added is exactly the missing piece: a **Spectate card on the eliminated player's own screen** (`app/ui/screens/sitting.js`, rendered only when `spectate` is active and the bracket is still in progress) that routes to the live `bracket-board` and records a real `SPECTATE_VIEW` ledger event (`Game#recordSpectateView` — the §13 "spectate rate" datum), with the shipped re-enter action unchanged beneath it (R60's SITTING choices). No chat, no emotes, no rewards for watching (that would leave play-earned return).
- **What failure teaches:** the room is filler between one's own duels — the social pull of sync is participation, not spectation; later envelopes should spend on faster re-entry paths (card 4's appointments or O6/O7 tuning), not on audience features.
- **§13 metrics it reads:** primary — spectate rate and elimination-to-re-entry time (both named §13 sync-health metrics), replay-after-loss (R49); secondary — the R51 2-brackets-in-48h rate; guard — lobby wait (O6) unchanged, since spectators re-entering can shift lobby mix (O7 human-share metric read beside it).

## Card 4 — Marquee scheduled brackets (manifest order #4)

- **O3 switch:** `legs_hypothesis = marquee_brackets`.
- **Behavior changed:** return at appointed times — players come back for a named bracket at a stated hour instead of (only) on impulse (D1/D7 return pattern shifts toward the scheduled slots).
- **Why it could:** appointment mechanics drive this audience's habits (R26): lock times structure the entire DFS/sportsbook day (dossier §3.1 — countdown clocks are a core presentation code), fantasy runs on a weekly appointment (dossier §3.3), and a quarter of bettors already wager daily on a schedule set by the slate (dossier A-5).
- **Minimum fair-test implementation (as built, f2):** **one scheduled marquee slot per day with countdown and reminder opt-in** (`app/engine/hypotheses.js:nextMarqueeSlot` — a **simulated** daily schedule, one slot at a fixed UTC hour computed purely from the clock, since no real ops calendar exists in this artifact; `app/ui/screens/lobby-entry.js` renders the named slot and live countdown only when `marquee_brackets` is active). The reminder opt-in is a **real, idempotent-per-slot ledger event** (`Game#optInMarqueeReminder` → `MARQUEE_REMINDER_OPT_IN` — the consented-events count §13 reads); no actual notification is delivered (client-only artifact — the opt-in is the measured behavior, delivery is a later-envelope rail). Same fees, same floors, same prizes (R20: only the arm variable changes; a boosted-prize marquee would test incentives, which is outside the R26 search space).
- **What failure teaches:** the game is impulse play — appointment structure adds friction rather than habit for a play-money artifact, and retention search should concentrate on always-available loops (card 5) and on-loss re-entry (cards 2/3).
- **§13 metrics it reads:** primary — D1 return (R46) and return-time distribution around the scheduled slots (every event anchor-joined per §13), weekly returner trajectory (R48, ungated diagnostic); secondary — brackets per week, reminder opt-in rate (a consented-events count), lobby human share (O7) at the marquee hour vs off-hours.

## Card 5 — PvE depth (manifest order #5)

- **O3 switch:** `legs_hypothesis = pve_depth`.
- **Behavior changed:** between-bracket power-building — players return to build stake through PvE between brackets, converting dead time into runway for the next entry (PvE sessions, PvE duels per player, then bracket re-entry).
- **Why it could:** runway before the next bracket (R26): below-floor players currently face a rebuild wall (R57 — below the tier floor the player rebuilds through PvE before re-entering), so PvE is already the mandated path back; giving house opponents *readable* tendencies makes the rebuild a skill loop rather than a grind, exercising the same research pleasure as card 1 (dossier A-3) against the R57 policy (equilibrium mix + 3% session drift — a tendency that is genuinely there to find).
- **Minimum fair-test implementation (as built, f2):** a **named house roster with readable tendencies and separate records** — when `pve_depth` is active, `Game#startPveOpponent` draws opponents by round-robin through the treatment's canonical `seedRoster` (`app/engine/pve.js:pveRosterOpponent` — R80's per-character personalities, NPC-tagged per invariant 8), and the PvE screen (`app/ui/screens/pve.js:renderRosterPanel`) posts each named opponent's element, F/W/A tendency mix, and **per-name W/L aggregated from real `PVE_DUEL_RESOLVED` ledger events** (`pveRosterRecords`). Anonymous PvE is unaffected when the card is inactive. Shipped ranges, drift, and rake unchanged (R57; risk note: `docs/risk-dossier.md` finding F-8 shows the shipped drift is exploitable by a perfect counter-player, so the fair test must run with the F-8 mitigation or accept measured farming as PvE engagement, and say which in the pre-registration).
- **What failure teaches:** brackets are the only loop that holds — PvE is runway, not retention; depth spend should go to bracket cadence (card 4) and re-entry (card 3), and PvE stays the minimum rebuild path.
- **§13 metrics it reads:** primary — PvE sessions and PvE stake built (named §13 metrics), PvE time and PvE duels per player in R51's windows (reported beside the 48-hour bracket count, per R51's dilution note); secondary — elimination-to-re-entry time, bust-to-top-up (R49) vs PvE-rebuild choice, tier advancement.

## Card 6 — Theme change (manifest order #6)

- **O3 switch:** `legs_hypothesis = theme_change` (applies **the named theme** — R22's door-race winner — to the retention configuration).
- **Behavior changed:** presentation-driven attachment — the same mechanics under the winning treatment raise replay-after-loss and reservation among *players*, not just clicks at the door.
- **Why it could:** presentation drives attachment (R26); the door race only measures pull at the door (R22's own reporting language), so a theme that wins acquisition has an untested claim on retention — this card is that test. The dossier's code analysis (§3.2: records-as-identity; §3.4: the character card as sports card) says presentation is where this audience stores attachment.
- **Minimum fair-test implementation (as built, f2):** **the door-race winner's treatment applied to the retention configuration** — when `theme_change` is active, `app/engine/overrides.js:effectiveTreatmentId` resolves the active treatment to **the last console run's recorded door-yield theme winner** (`lastDoorYieldThemeWinnerId`, written by the console's R22 door-yield report), reusing O1's own treatment-resolution mechanism rather than a parallel one; if no run has named a winner yet, the O1 selection stands. Both alternate skins are the complete R12 sets from `docs/selection-rubric.md` §3 → `docs/concept-cards.md` A1/F1, with every mechanic, price, and O-item frozen (R11, R20). The R13 mapping for each is recorded in the decision graph and `app/data/treatments/mapping.json`; brand acceptance (A3, invariant 5) precedes any participant-facing run.
- **What failure teaches:** presentation moves acquisition alone (R26) — theme is a door lever, not a legs lever; the real-money build can choose theme on acquisition economics and creative grounds without expecting retention gains.
- **§13 metrics it reads:** primary — replay-after-loss (R49) and reservation rate (R49a) against the concurrent incumbent baseline (R20: the original incumbent runs as baseline in every run); secondary — character recall in the open response (R22), D1 (R46), brackets per player; guard — the arm-variable-only configuration diff (invariant 12).
