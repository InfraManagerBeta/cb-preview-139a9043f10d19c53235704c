**Questions:** (1) Legs — does the persistent, multi-bracket game keep the target player playing and wanting the real thing? (2) Theme — which treatment best pulls this audience into play and toward reservation, for the same acquisition? (3) Price — which displayed entry price best converts play and reservation? (4) Risk — what breaks it, and does the fix hold?

# The incumbent configuration (§7–§13 — normative; written in the incumbent's nouns per R13)

## §7 Mechanics

- **R52 [LAW] Core loop.** A player summons a named character, enters it into 8-player single-elimination brackets, commits five moves in sealed simultaneous commitment per duel, and wins or loses staked value on the outcome — permanent records, a persistent world, a tier ladder toward a headline prize. Skill posture: outcomes are decided entirely by the committed moves; the operator's take is a rake; stake size changes how much value moves, and only that. [TESTED: the loop, in the bounded slice — R30.]
- **R53 [LAW] The duel** [CONSTRAINT: verified against the original on-chain implementation]. Moves Fire 0, Water 1, Air 2. Fire beats Air, Air beats Water, Water beats Fire; same move draws. Affinity: a character's element; playing it multiplies that round's contribution by 1.3, win or lose, for each character whose affinity matched. Weights by round [78, 79, 81, 86, 100] (sum 424). Draws contribute nothing.

```
roundWinner(m1, m2): if m1 == m2 → 0; d = m1 − m2; if d² == 4 → d = −(d >> 1); return sign(d)

duelScore(mv1, mv2, aff1, aff2):
  score = 0
  for i in 0..4:
    if mv1[i] == mv2[i]: continue
    d = mv1[i] − mv2[i]; if d² == 4: d = −(d >> 1)
    d *= 100
    if mv1[i] == aff1: d = floor(d × 1.3)
    if mv2[i] == aff2: d = floor(d × 1.3)
    score += d × WEIGHTS[i]
  return score / 100

powerTransfer(score, p1, p2, floor):
  if score < 0: return −powerTransfer(−score, p2, p1, floor)
  if score == 0: return 0
  ratio = sqrt(min(score / 424, 1.0))
  cp1, cp2 = p1, p2; if cp2 > 7·cp1: cp2 = 7·cp1; else if cp1 > 7·cp2: cp1 = 7·cp2
  transfer = round(cp2 × ratio ^ (cp2 / cp1))
  if p2 − transfer < floor: transfer = p2        // floor rule: full drain
  return transfer
```

- **R54 [LAW]** Transfer is always a fraction of the loser's stake. Win rate is independent of power. True tie (score 0): nothing transfers; a provably fair coin flip decides who advances. Draws = 5 − won − lost.
- **R55 [LAW] The floor (Blue Mold).** Each tier has a floor; a result leaving the loser under it drains the loser to zero, all of it to the winner; checked after the standard transfer; a true tie is exempt; minimum stake to enter a bracket equals its floor. Floor values are data (R84): **2 × the tier's re-entry bonus** — T0 50C, T1 50C, T2 500C, T3 500C, T4 5,000C, T5 5,000C, T6 50,000C. [ASSUMED: the 2× formula is a hypothesis under test; the zero-out frequencies it produces — ~57% at T0 for equal 100C stacks — are intended.]
- **R56 [LAW] Brackets.** 8 characters, single elimination, quarterfinal → semifinal → final, top half feeds top semifinal. The winner keeps stake won in duels plus the tier's headline prize from the external pool. Every bracket and win screen shows wins to the top — 3 per bracket × 7 tiers = 21 from a fresh T0 character, counting down. The win screen shows DUEL WON and the prize as separate lines.
- **R57 [LAW] Modes.** Brackets are synchronous (§11). 1v1 PvP exists as zero-stake test battles. PvE is the power-building loop: the player picks a house opponent within a range (floor = tier minimum; upper bound 2× the player's stake; hard cap 1.5× entry par for the highest eligible tier); real stake at risk; house opponents play the equilibrium mix with a 3% drift toward one element chosen per session; rake 5% on wins only; the floor rule is absent in PvE (an opponent at zero is replaced — new opponent, new tendency); below the tier floor the player rebuilds through PvE before re-entering brackets. [TESTED: 3% drift and 5% rake hold house exposure bounded against a perfect exploiter in simulation; ASSUMED: player experience of the range.]

## §8 Economy

- **R58 [LAW] Accounts.** CASH — liquid dollars in the wallet. Characters hold stake and exist until cashed out. Stake is always attached to a character. **20 CHEDDAR = $1, fixed.** Summon $10 → 100C (immediate cashout value $5; the gap is the price of competing for the prize).
- **R59 [LAW] The character comes summoned with a name** from the pool; naming is the pool's job alone, everywhere. The name is assigned and first revealed by the act of summoning — it appears on the summoned character, never on the pre-summon screen and never before an element is chosen. No name field, no preview, no re-roll.
- **R60 [LAW] State machine.** ACTIVE IN BRACKET → win: advance to the next tier (free the first time at each tier; entering tier N requires a live W > L record at tier N−1; tier 0 ungated; records per tier) · lose → SITTING: re-enter (pay the fee, receive the bonus) / cash out (stake → CASH at 20:1, character retires, record to the ledger) / sit indefinitely, free. ## §12 Interaction contract [LAW — R83]

Every press changes visual state within one frame of touch; an action over 100ms shows busy within that 100ms; a pressed control looks different from an unpressed one, always. One press, one action: the control disables until its action resolves, and every ledger-touching action is idempotent at the server with a per-action key. A control whose precondition is unmet renders a clearly disabled state — plainly distinct from the actionable state, a change of fill and weight, not opacity alone — and does not act until the precondition is met; a control never presents as actionable when it cannot act. No raw or developer error text reaches a participant surface: every blocked or failed action is explained in player language, and where an action would resolve the block, that action is offered in the same place. Targets ≥44×44pt with ≥8pt spacing, whole card as target wherever a card is the choice; the legacy tap delay is absent. Navigation begins visibly within 100ms; 300ms–1s shows busy; beyond shows progress; interactive elements hold position during async loads.

## §15 Invariant suite [LAW — R86] — machine-checkable, run in the model and in the product

1. For every resolved duel, transfer ≤ the loser's pre-duel stake, and the winner's gain equals the loser's loss.
2. Total stake across all characters plus all rake taken plus all prizes paid equals total stake summoned plus bonuses granted (ledger conservation), at every instant.
3. Stake is attached to exactly one character; the wallet holds CASH alone.
4. Win probability is invariant to stake: over any population of duels between equal-skill policies, win rate difference between high- and low-stake sides is within sampling error.
5. duelScore uses moves and affinities alone; the floor is checked after the standard transfer; a score of zero transfers nothing.
6. Every bracket entry satisfies stake ≥ floor and, for tier N > 0, a live W > L record at tier N−1.
7. Every ledger mutation carries a unique action key; replaying it changes nothing.
8. Every NPC-occupied seat renders the NPC tag on every surface listing that seat.
9. R1's forbidden strings appear in zero participant-facing render paths (automated scan per build).
10. Every gated metric in a report recomputes to the same value from the delivered raw events.
11. Every deposit event carries amount, preset-or-custom, balance before, time since bust, session number.
12. Within a run, arms differ in the arm variable alone (configuration diff is empty elsewhere).
